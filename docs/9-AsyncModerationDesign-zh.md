# LLM Shield 异步审核设计说明

本文说明 Python SDK 中 `ClientV2.ModerateStreamAsync(...)` 的设计目标、会话模型、关键时序，以及 2026-07-18 的两项修复内容。

适用代码位置：

- `volcenginesdkllmshield/api/llm_shield_sdk_v2.py`
- `volcenginesdkllmshield/__init__.py`

## 1. 设计目标

异步审核用于承接 LLM 增量输出场景，目标是在不改变服务端审核协议的前提下，同时满足以下要求：

1. 首包必须同步拿到审核结果，便于调用方在生成初期立即建立风险基线。
2. 中间分片尽量异步发送，避免每个 chunk 都阻塞业务线程。
3. SDK 对外仍然返回“截至当前最新已知结果”的审核响应，调用方不需要自己管理后台线程。
4. 尾包必须收敛到最终一致结果，不能遗留未审核内容。
5. 保持单会话串行发送语义，避免并发多发导致 `MsgID`、上下文内容和响应顺序错乱。

## 2. 对外接口

### 2.1 会话对象

```python
session = ModerateV2AsyncStreamSession(send_threshold=10)
```

- `send_threshold` 表示相对上次已审核快照的“新增内容阈值”。
- 默认值为 `10`，对应常量 `LLM_STREAM_SEND_BASE_WINDOW_V2`。
- 本次实现固定使用该阈值，不再做指数扩窗。

### 2.2 调用方式

```python
resp = client.ModerateStreamAsync(
    request=request,
    session=session,
    wait_timeout=0.2,
)
```

参数约束：

- `request.use_stream` 不能为空且不能为 `0`
- `session` 不能为空
- `wait_timeout` 不能为负数

返回语义：

- 可能返回最新审核结果 `ModerateV2Response`
- 如果当前分片还不足以触发新发送，返回最近一次缓存结果
- 在会话刚开始且首包审核失败前，不会返回伪造结果

## 3. 会话状态模型

`ModerateV2AsyncStreamSession` 维护以下几类状态：

### 3.1 内容累积状态

- `request`: 当前会话从首包到最新 chunk 的完整累计请求
- `stream_send_len`: 当前尚未触发发送的累计新增长度
- `last_request_content_len`: 最近一次已提交审核快照的内容长度
- `has_last_chunk`: 是否已经收到尾包
- `default_body`: 最近一次成功审核的响应缓存

### 3.2 并发控制状态

- `lock`: 会话级重入锁，保护所有共享状态
- `pending_thread`: 当前后台审核线程，任意时刻最多一个
- `pending_event`: 标记后台发送是否结束
- `result_cond`: 标记“是否产生了比调用前更新的审核结果”

### 3.3 结果版本与取消状态

- `result_version`: 每次成功收到新审核结果后递增
- `next_send_seq`: 后台发送序号，自增分配
- `pending_send_seq`: 当前在飞请求的发送序号
- `cancelled_send_seq`: 被判定失效的发送序号上界
- `pending_error`: 当前在飞请求产生的异常
- `need_flush_after_pending`: 在飞请求结束后，是否还需要基于更新后的累计内容继续补发

## 4. 核心时序

### 4.1 首包

首包进入时：

1. SDK 将当前请求深拷贝为会话快照。
2. 直接同步调用 `Moderate(...)`。
3. 审核成功后更新：
   - `default_body`
   - `session.request.msg_id`
   - `last_request_content_len`
   - `result_version`
4. 首包结果直接返回给调用方。

这样可以保证后续分片都在已建立的审核上下文内追加。

### 4.2 中间分片

中间分片会先追加到 `session.request`，然后分两类处理：

1. 若已有后台审核线程在执行：
   - 本次分片只做内容累积；
   - 根据“当前累计内容 - 在飞快照内容”计算 `new_content_len`；
   - 若达到阈值，或已经收到尾包，则设置 `need_flush_after_pending=True`；
   - 调用线程最多等待 `wait_timeout`，尝试拿到更新后的审核结果。

2. 若当前没有后台审核线程：
   - 计算“当前累计内容 - 最近一次已审核内容”的 `unsent_len`；
   - 只有当 `unsent_len >= send_threshold` 时才启动新的后台审核；
   - 未达到阈值则直接返回最近缓存结果。

### 4.3 尾包

尾包必须保证最终收敛：

1. 若没有在飞请求，SDK 直接对最新全量快照执行同步审核。
2. 若已有在飞请求，SDK 会将其标记为失效，再基于当前最新全量快照执行同步审核。
3. 老请求即使晚到，也不会再覆盖新结果。

这一步对应 `_flush_async_stream_session(..., force_until_idle=True, preempt_pending=True)`。

## 5. 后台补发机制

后台线程执行 `_run_async_stream_send(...)`，其关键语义是：

1. 用启动时拿到的快照发起一次审核。
2. 审核返回后，如果该发送序号已经被取消，则直接丢弃结果。
3. 如果结果仍有效，则刷新会话缓存。
4. 若发现请求执行期间又累计了足够多的新内容，或已收到尾包，则立即基于“当前最新全量快照”继续补发。
5. 直到没有新的补发需求，或该发送序号被取消后退出。

因此，对调用方来说，单个后台线程可以在一次生命周期里连续追平多个后续 chunk，不需要为每次分片都新建线程。

## 6. 2026-07-18 修复内容

今天的修复包含两部分。

### 6.1 修复一：异步流式审核与固定增长窗口

对应提交：`38e934e8d fix: 流式异步审核&固定增长窗口`

修复前的设计问题：

- 旧流式行为更接近同步节流发送，不能很好承接“业务线程持续写入，审核线程后台追平”的场景。
- 发送窗口存在增长策略，调用方较难预估何时会触发下一次审核。

修复后的行为：

- 新增 `ModerateV2AsyncStreamSession`
- 新增 `ClientV2.ModerateStreamAsync(...)`
- 单 session 同时最多只有一个后台审核线程
- 发送判定改为固定阈值 `send_threshold`
- 阈值判断基于“相对上次已审核快照的新增内容长度”
- 后台审核期间新增内容不会丢失，而是通过 `need_flush_after_pending` 在当前线程内继续追平
- 尾包支持抢占式同步收敛，避免最终结果落后于最新内容

直接收益：

- 审核触发点更稳定，可预测性更强
- 大模型逐字/逐 chunk 输出时，不会为每个片段都阻塞一次审核
- 会话内只保留一条有效审核链路，减少响应乱序风险

### 6.2 修复二：`wait_timeout` 等候期间刷新响应体返回

对应提交：`f87a1fb15 fix: time_wait等候过程刷新响应体返回`

修复前的问题：

- 中间分片进入 `wait_timeout` 等候时，只等待后台线程“结束”；
- 如果后台线程尚未结束，但在 `wait_timeout` 窗口内已经先产出了新的审核结果，调用方仍可能拿到旧的 `default_body`；
- 结果是“等到了新结果，却没及时返回新结果”，响应刷新不及时。

修复后的实现：

- 在 session 中新增 `result_cond` 与 `result_version`
- 每次新审核结果写入缓存时：
  - `result_version += 1`
  - `result_cond.notify_all()`
- 中间分片不再只等线程结束，而是调用 `_wait_for_async_result(...)`
- 该等待逻辑关注的是：
  - 当前调用开始后，是否出现了更新版本的审核结果
  - 或者超过 `wait_timeout`

修复后的返回语义：

- 如果 `wait_timeout` 内拿到了比调用前更新的审核结果，则立即返回最新结果
- 如果超时仍没有新结果，则继续返回上一次缓存结果
- 如果线程最终结束但没有产出新结果，则按原有错误/缓存语义处理

这个修复解决的是“等待期间结果已刷新，但返回值仍然滞后”的问题，不改变首包必须同步、尾包必须收敛的整体设计。

## 7. 一致性与并发保证

当前实现保证以下约束：

1. 同一 `session` 任意时刻最多只有一个有效后台发送任务。
2. 所有共享字段都在 `session.lock` 保护下读写。
3. 同步尾包可以抢占旧的在飞请求，旧请求结果不会覆盖新结果。
4. `default_body` 始终表示“当前会话最近一次成功审核得到的结果”。
5. 首包之后，SDK 会用服务端返回的 `MsgID` 回填到累计请求，保证后续审核上下文连续。

## 8. 错误处理语义

- 首包同步审核失败：直接抛错，不返回缓存结果。
- 后台审核失败且此前没有成功结果：在等待到异常后抛错。
- 后台审核失败但此前已有成功结果：
  - 若当前调用未等到更好的结果，则允许先返回旧缓存结果；
  - 后续 flush 或下一次等待会继续依据 `pending_error` 和补发状态决定是否抛错。

这意味着 SDK 优先保证流式调用可继续推进，同时保留最终暴露真实审核异常的能力。

## 9. 调用方使用建议

1. 每条生成流使用独立的 `ModerateV2AsyncStreamSession`，不要跨会话复用。
2. `wait_timeout` 适合设置为小于单次审核平均 RT 的短等待，例如几十到几百毫秒，用于尽量吃到最新结果而不长时间阻塞主流程。
3. `send_threshold` 越小，审核越及时，但请求频率越高；越大则更省请求，但风险暴露会更滞后。
4. 收到最终 chunk 后，必须使用 `use_stream=2` 调用一次尾包，确保最后一段内容被审核并完成会话收敛。
5. 若调用方自行并发访问同一个 session，会破坏设计前提；正确方式是单会话串行喂入 chunk。

## 10. 与同步流式审核的关系

- `ModerateStream(...)` 保留原有同步流式能力。
- `ModerateStreamAsync(...)` 是面向高频增量输出场景的补充能力。
- 两者的请求模型和审核协议一致，但会话对象不同，不能混用。

## 11. 后续可演进方向

当前实现已经满足异步审核主路径，但后续仍可考虑：

1. 增加显式关闭/结束 session 的接口，便于调用方做生命周期回收。
2. 将 `closed` 字段纳入真实状态机，目前该字段尚未参与外部关闭流程。
3. 为异步审核补充单元测试和并发场景测试，覆盖：
   - `wait_timeout` 内结果刷新
   - 尾包抢占在飞请求
   - 后台补发追平多个 chunk
   - 异常与缓存并存场景
